# 构建与发布

Arc Kit 从 0.1.0 起使用 GitHub Actions 构建的通用安装包公开发行。主应用、Runtime Host 和 Finder 扩展使用 ad-hoc 签名，**不提供 Apple Developer ID 签名或公证版**。更新包与订阅通过独立的 Ed25519 密钥签名；它证明更新来源，不代表 Apple 公证。

源码仓库为 `https://github.com/huixiangyang/arc-kit`；官网为 `https://arc-kit.com`；安装包保存在 GitHub Releases。官网源码在独立私有仓库 `arc-kit-site` 中，两个仓库独立提交。

首版 [v0.1.0 / build 56](https://github.com/huixiangyang/arc-kit/releases/tag/v0.1.0) 已于 2026-10-01 发布，源码为 `bd46b3c23ba8c4bf3d42c64a2b1b74d53c642c22`，由 [Release CI](https://github.com/huixiangyang/arc-kit/actions/runs/36848947270) 构建。已验证公开附件下载、SHA-256、DMG 完整性、解包后的嵌套签名、三组件双架构及随包许可证；用应用公钥验证了更新包和订阅，并确认修改内容后验签失败。官网版本数据与签名订阅均与发行附件一致。上述验证不包含真实跨版本安装重启、后台重注册或权限保留。

## GitHub Actions 安装包

| 流程 | 触发 | 产物 |
| --- | --- | --- |
| [Quality](../.github/workflows/quality.yml) | 分支 Push、PR、手动运行，或 Release 调用 | 本地化检查、离线回归、双架构构建，输出 DMG、ZIP、构建信息和 SHA-256；Artifacts 保留 7 天 |
| [Release](../.github/workflows/release.yml) | `vMAJOR.MINOR.PATCH` Tag，或指定已有 Tag 手动运行 | 复用 Quality 的同一份 DMG/ZIP，生成签名 appcast、发行索引、摘要，公开 GitHub Release 后更新 `updates` 分支 |

Release 不重新编译或替换 Quality 验证过的二进制。它先校验三组件版本、来源提交、资源及输入摘要，再生成最终附件。签名密钥不传给编译和 PR 工作流。

## 发布配置

应用更新签名使用 Secret：`SPARKLE_PRIVATE_KEY`。该密钥使用 Ed25519，签名与验证通过 Sparkle 官方工具执行；对应公钥固定在 `Build/Xcode/Products.yml` 的 `SUPublicEDKey`。维护者本机使用 Keychain 中的 `arc-kit-release` 账户保存私钥，不能提交导出的私钥、日志或截图。未来换机器需要保留这把密钥；不应随版本随意换钥。

`GITHUB_TOKEN` 仅在发布 job 拥有 `contents: write`，用于创建 Release 和维护 `updates` 分支。无需 Apple 证书或公证凭据。原生发版不再跨仓同步官网；官网所有下载入口直接进入 GitHub 最新 Release。Cloudflare 部署令牌仅保存在官网私有仓库的 `CLOUDFLARE_API_TOKEN` Secret 中，不传给原生编译或 Release 签名任务。

## 发版步骤

1. 修改 `Build/Xcode/Products.yml` 中三个组件的版本和递增 build，运行 XcodeGen 同步 Info.plist。在 `Documentation/Releases/<version>.md` 写明变化、安装条件和已知问题。
2. 提交并推送到 GitHub。Tag 必须指向已经审核的源码，名称与产品版本一致，例如 `v0.1.0`；已公开 Tag 不移动。
3. 推送 Tag，等待 Release 工作流。附件包含 `ArcKit-universal.dmg`、`ArcKit-universal.zip`、`BUILD-INFO.json`、`SHA256SUMS.txt`、`release.json` 和 `appcast.xml`。
4. 确认 GitHub Release 附件可下载、摘要一致，签名订阅已指向新版。官网下载按钮指向的 GitHub `/releases/latest` 链接自动跟进，无需为应用发版重新部署官网。

发行附件在带版本号的 GitHub URL 下保持不变。`updates` 分支只存 `release.json` 和签名 `appcast.xml`，在 Release 上传成功后才推进。版本数据发布失败时，旧更新通道保持不变；先核对已有 Release，再恢复发布数据，不能覆盖公开附件。

官网只维护介绍与使用指南，不再托管 ZIP、DMG 或版本清单。旧 `/download/` 和 `/downloads/*` 地址跳转到 GitHub 最新 Release。官网内容变化时在 `arc-kit-site` 单独部署；原生 Release 和 Sparkle 更新不依赖官网部署工作流。固定 `/updates/appcast.xml` 跳转继续保留。

本地打包入口只操作构建副本，不安装或启动应用：

```sh
bash Build/Scripts/package-app.sh \
  '.build/derived-data/Build/Products/Release/Arc Kit.app' dist/test-local
```

输出目录必须不存在。完整 App 由 Xcode 构建，包含两个 CPU 架构、Host、Finder 扩展、Framework、语言资源与许可证；SwiftPM 产物用于预览和回归，不作为安装包。

## 可选 CloudKit 签名构建

剪贴板源码支持本地历史与 CloudKit 私有库同步；**默认 `project.yml` 和现有 ad-hoc CI 不开放 iCloud**。2026-11-10 尚无 Developer 团队、容器和匹配描述文件，未执行真实云端联调，也未改变当前发行通道。

准备条件由维护者完成：

1. Apple Developer Program 团队，以及本机 Keychain 中有效的 Developer ID Application 签名身份。证书、私钥和密码不写入仓库或聊天。
2. 为主应用 `com.archalo.arckit` 启用 CloudKit、关联 `iCloud.*` 容器，并取得包含这些 entitlement 的 Developer ID provisioning profile。Host、Finder 扩展不访问 CloudKit；各组件仍按实际 App ID 与签名要求配置，不共用主应用的 profile。
3. 初始化 Development schema：private database、自定义 zone `ArcKitClipboard`、record type `ArcKitClipboardItem`，`payload` 必须为 **Encrypted Bytes**，`image` 为 Asset。完成开发环境验证后发布 schema 到 Production；不要先把 payload 建成普通 Bytes 再尝试切换加密。
4. 两台用于验收的 Mac 使用同一 Apple 账户、相同容器和相同环境；新签名身份的权限、Host 注册和更新路径另做安装验收。

[Apple 官方能力表](https://developer.apple.com/help/account/reference/supported-capabilities-macos)说明 Developer ID 的 CloudKit 支持；容器和加密字段要求见 [Apple 配置说明](https://developer.apple.com/documentation/cloudkit/enabling-cloudkit-in-your-app)及[加密示例](https://github.com/apple/sample-cloudkit-encryption)。

配置齐备后使用覆盖入口，非敏感标识由构建变量传入：

```sh
xcodegen generate --spec project-cloudkit.yml --project .build/xcode
xcodebuild -project .build/xcode/ArcKit.xcodeproj -scheme ArcKit \
  -configuration Release -destination 'generic/platform=macOS' \
  -derivedDataPath .build/derived-data-cloudkit \
  ARCKIT_DEVELOPMENT_TEAM="$TEAM_ID" \
  ARCKIT_CLIPBOARD_CONTAINER="$CONTAINER_ID" \
  ARCKIT_CLOUD_PROFILE="$PROFILE_NAME" \
  ARCKIT_CLOUD_ENVIRONMENT=Production \
  ARCHS='arm64 x86_64' ONLY_ACTIVE_ARCH=NO build
```

`project-cloudkit.yml` 指定主应用 CloudKit entitlement、手动签名和 profile；正式签名入口使用 Release。开发环境测试使用相应 Apple Development 身份和开发 profile，并把环境设置为 Development；环境必须与实际 profile 匹配，不能只修改 Info.plist 来切换。无签名编译只能验证源码，不能使 iCloud 可用。

**现有 `package-app.sh` 会重新执行 ad-hoc 签名，不能用于保留 CloudKit 签名的产物。** 在正式发行云端版本前，维护者还需为已签名 App 接好保持嵌套签名／描述文件的打包及公证流程，验证最终包的团队、容器、环境、profile 和各组件签名，再执行双 Mac 同步与升级验收。当前签名覆盖配置不是已完成的发行流水线。

默认工程可重新运行 `xcodegen generate --project .build/xcode` 恢复生成；生成工程不入库，团队与容器信息不写死到源码。状态、限制和完整验收条件见[剪贴板](剪贴板.md)。

## 自动更新

使用 Sparkle 2.10.0，移除原先自行实现的 JSON 清单、下载状态机与打开 DMG 流程。应用默认每天自动检查；用户可关闭，也可以选择自动下载并在退出时安装。手动检查入口位于应用菜单和“系统设置 → 关于”。界面预览、SwiftPM 命令行产物和单元测试不会启动更新器。

固定订阅地址为 `https://arc-kit.com/updates/appcast.xml`，由 Pages 转向公开仓库 `updates` 分支中的签名文件。安装包 URL 指向 GitHub 对应版本的 Release 附件。通过 Sparkle 官方工具生成订阅，并对订阅与压缩包分别校验 Ed25519 签名；应用开启 `SURequireSignedFeed` 与 `SUVerifyUpdateBeforeExtraction`，不继续使用域名白名单代替更新包身份校验。

安装更新需要退出主应用。现有应用终止流程负责等待设置写入、结束素材变更、停止并注销 Runtime Host；不能直接强杀进程来完成更新。升级后仍需验证后台重新注册、Finder 扩展及既有权限。自动更新不操作用户数据目录，旧开发版需先手动升级到包含 Sparkle 的公开版本。

## 保留数据升级

1. 在旧应用选择“退出 Arc Kit”，等待设置保存、Host 注销及 Worker 结束。关闭设置窗口不等于退出；其他登录用户也应退出旧版本。
2. 备份旧应用、一致的 SQLite 数据库和素材。升级不默认清空用户数据或重置授权。
3. 整包替换 `/Applications/Arc Kit.app`，核对三组件版本、签名及 Finder 扩展注册路径，避免系统引用开发产物。
4. 启动主应用，检查迁移、原设置、后台及权限。按本次变更验证真实操作，再检查正常退出与重启。

ad-hoc 候选包升级曾发生 `Launch Constraint Violation`，表现为主应用运行而 Host 被系统阻止。正常退出、刷新当前应用注册并启动可恢复已有案例，但更新时序与签名约束根因仍待解决；不应关闭系统安全机制。

回退前先核对旧程序能否读取当前数据格式。需要恢复旧数据时使用匹配的备份，并保留升级后现场，不把新版数据库交给不认识其格式的旧程序。

## 离线迁移与恢复

以下入口只用于仍使用旧文件存储的安装，或主应用无法启动的恢复场景。先正常退出全部组件并备份，确认目标路径；不要对已初始化的数据根重复导入。

```sh
"/path/to/Arc Kit.app/Contents/MacOS/Arc Kit" --import-legacy-storage \
  "$HOME/Library/Application Support/Arc Kit" "$HOME/.arc-kit"
```

导入目标必须不存在。程序校验旧配置、事务、资源及数据库完整性后启用目标；旧目录保留，不搬入旧日志与备份。桌面可能仍引用旧素材，不要立即删除源目录。日常运行只读写 SQLite，不保留旧文件双写。

主应用因数据损坏无法启动时，可在组件退出后用完整备份恢复：

```sh
"/path/to/Arc Kit.app/Contents/MacOS/Arc Kit" --restore-storage \
  "/path/to/ArcKit.arckitbackup" "$HOME/.arc-kit"
```

恢复需取得 app/host/worker 独占锁，校验备份及资源后替换数据库，并保留恢复前数据库。跨目录恢复使用完整数据包；元数据备份依赖原素材仍存在。不要恢复旧 runtime 身份或防重放文件。

## 验收与记录

注册、连接、权限和执行结果分别核对。Finder 使用可恢复的测试文件；鼠标使用真实设备与目标应用确认方向和手感；窗口覆盖前台目标及相关显示器。权限覆盖拒绝与恢复，数据恢复使用独立临时目录。

保存产物、版本、验证条件与未验证项目。测试数量、PID、个人机器名和整段诊断日志留在本地证据中；公开版本说明只描述功能变化、已知限制和适用范围。
