# 菜单栏管理与美化

在设置侧栏打开“菜单栏”，可以管理收纳、搜索图标、配置快捷键和预览外观。功能默认关闭，当前源码尚未安装或发布。

**macOS 27 已改用系统溢出收纳。** 临时自有图标检查确认分段占位能收起图标，并能在外屏恢复；另一次检查中一块副屏在 400ms 后仍保留旧布局，多屏恢复时序尚未闭环。系统外观应用仍未实现。

## macOS 27：使用系统溢出区

1. 开启菜单栏收纳，初始状态显示全部。
2. 按住 ⌘，将需要收纳的图标拖到双向箭头分隔线左侧；常用图标留在展开控件右侧。保留分隔线与展开控件的位置，只移动应用图标。
3. 点击“收起”，或左键点击展开控件。左侧图标进入 macOS 自带的溢出菜单；再次点击控件或选择“显示全部”恢复。
4. 通过系统溢出入口取用图标，也可使用 Arc Kit 的“搜索全部菜单栏图标”。

Option 点击控件显示全部，右键菜单提供收起、显示全部和全图标搜索。设置页、⌘K 和可配置快捷键均保留独立恢复入口。菜单栏本身放不下图标时，“显示全部”只能撤除 Arc Kit 的收纳占位，系统自身仍可能保留溢出项。

### 为什么改为分段占位

macOS 27 将菜单栏内容交给系统代理合成。实测中，小宽度分隔线能够推动左侧图标，超宽分隔线却可能被丢弃，让图标重新出现；溢出项目的 AX 和 AppKit 位置也不会可靠地变为负坐标。

运行实现根据各屏宽度及刘海右侧可用区计算单段长度，使用多个自有 `NSStatusItem`，不修改第三方应用配置、不合成拖拽。所有额外占位位于可见分隔线右侧，展开时长度为 0；系统仍会为这些项目保留间距。一次三屏检查使用 10 段、每段 267pt。

收起后连续两次确认自有按钮宽度与请求一致，才更新请求状态。这里确认的是占位应用，不是逐个图标的可见性。截图用于检查实际结果，不将 AX 的重叠位置解释成可靠分区。

### 当前能力边界

- **深度收纳与普通区筛选在 macOS 27 暂不开放**。设置页、控件菜单、⌘K 和搜索面板同步移除相应操作；不能确认归属的图标不会混入普通收纳。其他系统保存的深度区意图保留在统一配置中，本机不创建深度分隔线。
- **全图标搜索保持独立可用**，不新增可见坐标或分区凭据前提，也不默默将“普通区”请求改成“全部”。
- 显示器、Space 或应用变化时先显示全部，取消旧清单与图标取用，并等待当前屏幕及自有控件宽度连续两次稳定，才重新允许收起。每次最多等待约 1 秒，只回读、不重发动作；超时保持释放占位，可点击“显示全部”重新检查。
- 若新的布局需要更多占位，仍提示关闭并重新开启收纳。系统没有可靠的公开插入位置接口，不能在用户图标中间自动补入占位或删除重建分隔线；保留用户位置优先于自动扩容。
- 设置页图标清单是只读观察，不支持页面内拖拽排序。同一进程运行中新增图标还没有可靠事件监测，不能承诺自动归入常驻区。
- 系统溢出菜单由 macOS 控制，不是隐私隔离区。

## macOS 13–26：离屏分区

这些系统保留已有的常驻、普通收纳和可选深度收纳路径，目标系统实机验收仍待完成。原生排列为：

```text
深度图标 | 深度分隔线 | 收纳图标 | 收纳分隔线 | 常驻图标 | 展开控件
```

“收起”请求收起普通区和深度区；“展开收纳”只展开普通区；“显示全部”恢复所有分隔线的普通宽度。左键切换收起与普通展开，Option 点击显示全部。

新增收起前等待两次一致的可见边界，变更后确认完整快照及离屏边界，每次等待最多约 1 秒，只重读、不重发动作。占位宽度为最大显示器宽度加 100pt。无法确认时原生 driver 撤回本次宽度变更；设置页或控件请求失败后，管理服务按恢复策略显示全部。

普通区筛选要求发现前后的屏幕、边界和原生代次一致，且属于面板目标显示器。跨界、错序、宽度未稳定、显示器不匹配和同高度屏幕的歧义坐标均不猜归属。没有凭据时数量显示“—”，不显示假零或回退到全部图标。

普通区取用只展开普通区，发送动作前再次读取原对象的位置和当前分区。图标移入深度区或边界失效时拒绝并要求刷新，不能因为搜索命中而暴露深度区。

## 搜索并取用原生图标

从设置页、控件右键菜单、⌘K 或已配置的快捷键打开“搜索全部菜单栏图标”。面板出现在指针所在显示器，按应用名、状态项描述或 Bundle ID 搜索；上下键选择、回车取用、Esc 或点击外部关闭。输入法组合状态和文本编辑修饰键不会触发图标动作，原生控件保留自己的键盘处理。

面板随结果数量调整高度，上沿和搜索框固定；异常状态保留足够空间显示原因。悬停选择不驱动滚动。设置页与搜索面板都排除本进程自有控件，避免占位项目充满清单。

发现过程在线程池读取 AX，主线程准备进程和屏幕快照、接收结果。取消、刷新或关闭后，旧结果不能回填；会话只在内存中持有本次 AX 引用，不写入 SQLite。

选择图标时核对会话 UUID、PID、进程启动时间、Bundle ID、辅助功能权限和屏幕快照。全图标入口先撤除收纳占位，再向原来的 AX 对象发送一次 `AXShowMenu`，否则使用 `AXPress`。不猜坐标、不启动替代应用。令牌在发送前消费；超时可能已经执行，不能自动重放，也不重新弹出面板抢走菜单焦点。再次打开时保留未解决反馈。

系统接受 AX 请求不等于菜单已经显示。第三方菜单的实际结果、离屏/刘海项取用及键盘交互仍需实机验收。使用后保持展开，避免打断原生界面。

## 快捷键和外观

两项快捷键分别控制全图标搜索和显示全部，默认关闭。可选 `⌃⌥M`、`⌃⌥⇧M`、`⌃⌥⌘M` 或关闭，两项不能相同；当前没有自由录制。

主应用使用 Carbon 注册热键，不监听键盘文本、不增加 Host endpoint。仅保存成功后注册，冲突报告原始 OSStatus，不覆盖其他应用的组合。停用、退出和数据恢复会注销，旧注册 ID 不能触发新绑定。

“原生 / 悬浮 / 分段”、不透明度和圆角已进入统一设置，支持自动保存、撤销重做、重置及备份恢复。刘海开关只改变预览示意。**系统外观尚未应用**：临时实测中，23/24 层不能完整显示背景，25 层又会给文字和图标一并染色。该着色叠层已从当前开发检查中移除，页面没有“已应用”状态或占位应用按钮。

## 权限、存储和恢复

- 状态项、搜索面板和热键都由主应用拥有，不新增常驻服务或 Runtime Host endpoint。配置只推进 data revision，不重连窗口/鼠标 Host。
- `AppSettings.menuBar` 使用主应用统一 schema；菜单栏及快捷键引入时升至 26，当前整体版本以 `AppSettings.schemaVersion` 为准。旧 JSON 契约直接拒绝。
- `menu-bar-management-v1` 和 `menu-bar-shortcuts-v1` 迁移为旧 SQLite 补充默认关闭的功能及快捷键，保留已有数据。配置提交失败不改变原生控件。
- AX 探测和搜索需要 **Arc Kit 主应用**的辅助功能权限，不能使用 Runtime Host 授权代替。探测不截屏、不打开第三方菜单、不弹出授权申请；未获授权时显示设置入口。
- `showMenuBarIcon` 继续只控制原有 Arc Kit 快捷面板，新分隔控件由菜单栏功能开关独立管理。
- 新应用启动、Space/显示器变化时先显示全部，独立推进恢复代次；旧 AX 清单、分区凭据和取用会话立即失效。尚未开始执行的旧任务也先检查代次，不会在恢复之后短暂重新收起。
- 休眠时释放占位并暂停收纳及取用，迟到的显示器通知不会解除暂停；只有唤醒才重新等待稳定读数。停用、数据恢复和退出取消全部恢复任务并删除控件，旧确认结果不能重新启用服务。
- 显示全部始终直接释放占位；全图标搜索和取用不新增分区或稳定坐标前提。稳定窗口只限制新的收起与普通区取用，超时不会自动缩小恢复入口的能力。
- macOS 保存自有状态项位置，SQLite 不复制排列。AX 观测 UUID、PID、坐标和数组顺序均不作为跨启动身份。
- 功能图标使用 Lucide，中英文维护于 `MenuBar.xcstrings`。

## 开发入口

在原生仓库根目录执行：

```sh
swift build --product ArcKitApp

# 可见设置预览，使用独立调试库，不创建真实菜单栏控件。
.build/debug/ArcKitApp --ui-debug --menu-bar-settings

# 正式页面离屏导出，不读取真实图标、不显示窗口。
.build/debug/ArcKitApp --menu-bar-render .build/menu-bar-development/render-01

# 只读真实 AX 清单，不发送图标动作。
.build/debug/ArcKitApp --menu-bar-probe .build/menu-bar-development/probe-01

# 需明确授权：临时自有状态项的收起、展开和撤除，不安装应用。
python3 Build/Scripts/check-menu-bar-native.py .build/menu-bar-native-checks/check-01

# 需明确授权：仅对比分段占位，不走产品状态机。
python3 Build/Scripts/check-menu-bar-native.py --widths .build/menu-bar-native-checks/widths-01
```

输出目录必须不存在，权限为 `0700`。旧 `--menu-bar-lab` 已删除，不维护第二套界面。

离屏导出目前为 30 张 PNG，覆盖三个页面的中英文、深浅色、480pt 窄布局、搜索状态，以及旧系统的离屏分区页和普通区筛选夹具。夹具明确标注演示数据，不表示当前 macOS 27 支持普通区。预览服务不构造 native driver、注册热键或显示真实面板。

实机监督脚本调用 Debug 的 `--menu-bar-native-check` 或 `--menu-bar-width-check`，均在生产存储初始化前分流。临时项目显式使用唯一 `autosaveName`，撤除时清除；**省略名称会让 AppKit 自动选名，并不能隔离系统记忆**。检查不启动 Host、不注册快捷键、不操作第三方图标。

有屏幕录制权限且系统支持时，ScreenCaptureKit 只截取各屏顶部区域，不主动申请权限；无权限则记录缺失。实机报告及只读清单含个人菜单栏信息，分享前检查。

进程内有 30 秒撤除期限和终止信号处理；监督脚本在 40 秒后只终止自己启动的子进程，3 秒后仍未退出才强制结束。正常结束先释放状态项，再记录剩余数量。实机退出码 `4` 表示占位/分区请求未确认，`124` 表示超时；`0` 不能代替截图验收，宽度实验也不宣称产品状态机通过。

Release 在存储初始化前拒绝全部 `--menu-bar-*` 参数。其他开发退出码：`1` 输出失败，`2` 参数或构建类型错误，`3` 只读探测的权限或几何未就绪。

## 证据与后续验收

### 已核实的系统行为

- 2026-10-22 只读观察发现 15 个项目，只有 3 个具备唯一 AXIdentifier 候选；不是重启身份保证或当前完整清单。
- 2026-10-23 初始超宽方案请求 5220pt，按钮回读为 5000pt，坐标不构成合法离屏分区；旧检查以 `4` 结束，记录在 `.build/menu-bar-native-checks/20261023-stable-layout/`。
- 新的唯一名称宽度实验确认 128/256/384/512pt 能推动自有图标；768pt 时图标进入系统溢出，2660pt 则让图标重新出现。记录在 `20261023-widths-fresh-names/`。`AXHidden` 不受这些状态项支持，不能作为可见性证明。
- 分段实验使用 10×267pt，实际截图中两块外屏的测试图标收起后消失、展开后恢复；内建屏初始已溢出，不能用它证明从可见到收起。记录在 `20261023-segmented-spacing/`。
- 接入正式 driver 后，`20261023-system-overflow/` 的占位请求检查通过，截图确认收起；一块外屏在恢复后 400ms 的截图中仍保留旧溢出布局，另一块已恢复。随后增加只读等待的复测 `20261023-overflow-settled/` 运行时仅连接内建屏，不能补齐该外屏恢复证据。
- 检查结束均撤除自有状态项，监督进程确认退出。安装版、生产数据和 Runtime Host 未被替换或重启。

外屏 `NSStatusBar.thickness` 实测为 22pt，顶部保留区为 31pt；共享屏幕快照已采用每屏顶部保留区。分段方案参考 [MenubarHide 的 macOS 27 记录](https://github.com/junior-rj/menubar-hide#macos-27)，按本项目生命周期独立实现，授权见 [MIT 声明](../Licenses/MenubarHide-MIT.txt)。AppKit 的可见性限制也见 [Apple 的 isVisible 文档](https://developer.apple.com/documentation/appkit/nsstatusitem/isvisible)。

### 2026-10-28 环境恢复实现

- 环境恢复现在具有独立代次，清理旧清单、取用会话和未完成收起；睡眠、布局更新、确认失败与可操作状态分别处理。
- 原生确认只检查 AppKit / WindowServer 屏幕快照一致，以及自有控件已经回到展开宽度；连续两次符合才结束等待。它不证明系统代理已在每块屏幕上恢复第三方图标。
- 恢复失败时不重建分隔线、不重发收起，保留“显示全部”的即时恢复与重试入口。全图标搜索的原有使用条件不变。
- 新增 3 项隔离回归已通过，覆盖旧 AX 结果迟到、连续环境变化、休眠中的切屏通知、恢复失败重试、配置重装保持恢复门禁、停用后的迟到确认和稳定读数判定。集中构建与回归日志为 `.build/development-20261028/tests.log`；真实外屏恢复和原生菜单取用仍未验收。

### 下一步

1. **多屏恢复与排列**：在外屏重新连接后验证系统代理的更新时序、用户重新排列、自动隐藏、Space、睡眠及热插拔；减少展开时额外占位保留的间距。显示全部后的原生溢出菜单取用仍需验证。
2. **管理闭环**：完成第三方原生菜单取用、真实快捷键/输入法/冲突检查，以及新图标发现、设置页排序和身份重启验证。不以修改页面顺序代替真实排列。
3. **外观应用**：选择能分离系统背景与菜单内容的绘制路径，再验证交互穿透、全屏、多屏和空闲能耗；当前保留预设编辑和示意预览。
4. **环境联动**：将菜单栏预设与壁纸、窗口场景组合，分别反馈执行和恢复结果。
